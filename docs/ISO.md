# The ISO build

How the installer and rescue disc is made, what is checked, and how to change it safely. The user's side is in [USER-GUIDE.md](USER-GUIDE.md).

A Catalyst build takes hours, so everything that changes the image is collected in one set of files, rendered from one place and checked at the end by `scripts/verify-iso.py`. Nothing in this document claims a real-hardware boot: the checks are static, plus QEMU runs by the VM harness.

## 1. Pipeline

```
scripts/build-iso.sh  (host)                       iso/builder-entrypoint.sh  (container)
 validates inputs and free space                     reproducible source archives (.tar.zst)
 builds the pinned builder image  ─────────────►     overlay + Manifests, rendered specs
 docker run --name gentoo-iso-<hash>                 stage1 decision (iso/stage_reuse.py)
   log, signals, OOM hint                            stage3 seed + Gentoo commit: signatures checked
 checks the published files                          Catalyst stage1  ─►  receipt
                                                     Catalyst stage2  ─►  ISO
                                                     scripts/verify-iso.py  ─►  publish + manifest
```

1. **Builder image** (`iso/Containerfile`): a pinned `gentoo/stage3` image with Catalyst, git, rust-bin, the Gentoo OpenPGP keyrings and `xorriso`. The Gentoo tree in it is first bootstrapped from a GitHub tarball (only so that Portage can install the tools above), then replaced by the exact commit of `iso/pins.env`, fetched with git and accepted only when it carries a good signature of the key named by `GENTOO_TREEISH_SIGNER_FPR`. The keyrings come from the bootstrap tree, so this protects against a changed commit or a swapped signer, not against a compromised bootstrap; the pin is the reviewed decision.
2. **Source archives**: `gentoo-live-installer`, `hwmonux` and `portagehub` are packed reproducibly (sorted, fixed mtime) into `.tar.zst` distfiles. Their names and versions come from the ebuild file names in `packaging/gentoo-overlay`; nothing else repeats a version. `ebuild ... manifest` writes the Manifests; the same overlay is shipped inside the image for the target systems.
3. **Rendering** (`iso/render-config.py`): the specs, `portage/make.conf` (+ `make.conf.extra`), `README-live.txt` and everything below `iso/cd_overlay` come from one token map. Tokens: `@BUILD_DIR@ @TREEISH@ @VERSION_STAMP@ @STAGE3_BASENAME@ @ISO_NAME@ @VOLID@ @BOOTARGS@ @JOBS@ @LOAD_AVERAGE@`; an unexpanded token is an error. `ISO_VOLID` and `ISO_BOOTARGS` in `iso/pins.env` are the only source of the volume label and the kernel arguments, for `livecd/volid`, `livecd/bootargs` and every `linux` line of `grub.cfg`.
4. **Overlay ownership** (`iso/lib/overlay.sh`): inputs are copied without the builder's owner, then chowned to root with directories 0755, executables 0755 and other files 0644. Without this the image carried the build user's uid (1000, which is the live user) on `/etc` and the whole overlay.
5. **Stage1/stage2**: Catalyst runs through `iso/catalyst-no-loop.py`, which uses a verified directory snapshot instead of a loop-mounted squashfs, bounds ninja, and appends the settings from `iso/make_conf_keys.py` to Catalyst's two `make.conf` rewrites. The build chroot gets all of them; the rewrite that ends in the image gets only `LIVE_KEYS` (and `FEATURES` without `buildpkg`), and Catalyst's builder-only `DISTDIR`/`PKGDIR` lines are removed. A job count is therefore never frozen into somebody's machine; livecd-tools' `autoconfig` writes `--jobs=$(nproc)` at boot.
6. **Verification and publishing**: `scripts/verify-iso.py` must pass before the ISO is copied to `/dist`; then `.sha512`, `.blake2b`, `.packages.txt` and `.manifest.json` are written.

Catalyst 4.2 facts the design relies on (checked in `catalyst/targets/livecd_stage2.py`, `base/stagebase.py` and `/usr/share/catalyst/targets/`):

* `livecd/overlay`, `livecd/readme`, `livecd/rm`, `livecd/unmerge`, `livecd/rcadd`, `livecd/volid`, `livecd/bootargs` are valid `livecd-stage2` keys.
* Order: `build_kernel`, `bootloader` (writes `boot/grub/grub.cfg`, copies `/boot/memtest86plus/*` and the README to the ISO tree), `preclean`, `livecd_update` (writes `/etc/motd`, `make.conf.old`), `root_overlay`, `fsscript`, `rcupdate`, `unmerge`; then `remove` (`livecd/rm`), `empty`, `clean` (rewrites `make.conf`), `target_setup` (makes `image.squashfs`), **`setup_overlay`** (`rsync -a livecd/overlay/` onto the ISO tree, so our `grub.cfg` replaces Catalyst's), `create_iso` (`grub-mkrescue`). `root_overlay` therefore replaces `/etc/motd`; the live `make.conf` can only be fixed by the wrapper because `clean` runs after the fsscript.
* `rc-update.sh` exits 0 even when every `rc-update add` fails, so `verify-iso.py` checks the runlevel links and init scripts itself.
* The spec parser splits **every** line that contains a colon into key and value, strips `#` comments, and treats `%` as interpolation; list entries and values must not contain `:` or `%` (`tests/iso/test_specs.py`).

## 2. `scripts/build-iso.sh`

| Option / variable | Meaning |
|---|---|
| `--check` | Validate tools, pins, inputs, free space; start nothing, create nothing. |
| `--reuse auto` (default) | Reuse the previous stage1 when nothing that goes into it changed; else build stage1 fresh. When only the project's own packages changed that is shorter, because the binary package cache serves everything else, and the project's packages are always built from this tree. |
| `--reuse-stage1` | Same as `--reuse auto`. |
| `--reuse none` | Always build everything. Use it for releases when in doubt. |
| `--stage2-only`, `--reuse stage1` | Run only stage2; fails unless the receipt matches. |
| `--stage1-only` | Build stage1 and its receipt, no ISO. |
| `--test-key-file FILE` | Build a **TESTKEY** image with this OpenSSH public key as root login. Requires `ISO_DIST_DIR`, outside `dist/` (`dist/` itself and every directory below it are refused; for example `build/test-dist`). `GENTOO_TEST_SSH_PUBLIC_KEY` does the same. |
| `--verify ISO [--flavor release\|testkey]` | Run `scripts/verify-iso.py` on an existing ISO. |
| `--sign-key KEYID` | After a successful release build, write detached, armoured OpenPGP signatures `<iso>.sha512.asc` and `<iso>.manifest.json.asc` with your key (16 or 40 hex digits) and check them. This runs on the host after the container has exited, so the key never enters Docker; the checksum file names the ISO hash, so it covers the ISO. Refused for a test-key build. |
| `--clean`, `--clean-packages` | Remove chroots, `*.partial` files and stage1 archives beyond `ISO_KEEP_STAGE1` (default 2); the second also empties `catalyst/packages`. |
| `JOBS`, `LOAD_AVERAGE` | Parallelism (default 2 jobs, load average 2x). |
| `BUILD_MEMORY` | Container memory and swap limit, default `8g` (`^[1-9][0-9]*[mMgG]$`); a warning if the host has less than that plus 2 GiB available. |
| `BUILD_MIN_FREE_GIB` (45), `ISO_DIST_MIN_FREE_GIB` (6), `DOCKER_MIN_FREE_GIB` (10) | Free space on the cache, output and Docker storage filesystems; filesystems are summed per device. |
| `ISO_CACHE_DIR`, `ISO_DIST_DIR`, `ISO_LOG_DIR` | Default `.cache/iso`, `dist`, `<dist>/logs`. |
| `ISO_SECCOMP` | `unconfined` (default) or `default`. Catalyst needs `mount(2)`/`chroot(2)`; try `default` and report if a build works. AppArmor is set to unconfined only where Docker reports it. |

Inside the container, `iso/builder-entrypoint.sh` is driven by the variables the script passes with `--env`: `BUILD_MODE` (`full`, `auto`, `stage1-only` or `stage2-only`, chosen from `--reuse` and the receipt; `reseed` is not reachable from the script, only a container started by hand with that variable runs it), `ISO_FLAVOR` (`release` or `testkey`), `JOBS`, `LOAD_AVERAGE`, `ISO_KEEP_STAGE1` and the host user's `HOST_UID`/`HOST_GID` (the outputs are handed back to that user, and the verifier looks for image files that carry those ids). `PROC_MEMINFO` only exists for the tests of the memory check. Do not set these by hand; use the options above.

What the script guarantees: one build per cache (`flock`), a container named `gentoo-iso-<12 hex of the cache path>` that is stopped on Ctrl-C or SIGTERM (`docker stop --time 120`, exit 130 or 143), a timestamped log with the path printed first, the last 40 lines on failure, the last `Emerging (` line and a `BUILD_MEMORY`/`JOBS` hint when Docker says the container was OOM-killed, outputs handed back to the invoking user, and no host block devices. Inside, `iso/lib/run.sh` makes Catalyst a child that receives the signal.

Disk use measured on the r19 build: Catalyst store 40 GiB (builds 23 GiB with five stage1 archives of 2.9 GiB, chroots 15 GiB, binary packages 1.4 GiB, snapshots 0.5 GiB), distfiles 1.7 GiB, cargo 0.6 GiB, plus the 2.8 GiB ISO and Docker's image layers. `--clean` and `ISO_KEEP_STAGE1` keep that bounded. The binary package cache that matters is `catalyst/packages/23.0-default/` (Catalyst keys it per target); the former separate `binpkgs` directory was never used and is gone.

### Flavours

| | release | testkey |
|---|---|---|
| ISO file | `gentoo-installer-amd64-<release>-<stamp>.iso` | `gentoo-installer-amd64-<release>-<stamp>-TESTKEY.iso` |
| Volume label | `GENTOO_INSTALLER_AMD64` | `GENTOO_INSTALLER_TESTKEY` |
| Root | locked (`!` in `/etc/shadow`) | locked password, key-only SSH from `root/.ssh/authorized_keys` (the drop-in `90-installer-vm-test.conf`, which sorts before the live package's `PermitRootLogin Yes`) |
| sshd | in `livecd/rcadd` of the spec, so it starts at every boot (section 6, "Remote access") | the same one entry; the builder no longer edits the spec |
| Banner | none | "TEST BUILD ..." on `/etc/issue` and `/etc/motd` |
| `verify-iso.py` | refuses the test artifacts (key, marker file, test drop-in, host keys), requires a locked root, and the first `PermitEmptyPasswords` of the sshd drop-ins to be `no` | requires the key, the marker file and the test drop-in, and `PermitRootLogin prohibit-password` first |

The names are derived in `iso/lib/naming.sh` (used by the script and the container) and mirrored in `verify-iso.py`; a test keeps them equal. A boot-menu volume label only has to match between `livecd/volid` and the `root=live:CDLABEL=` argument, so nothing else in the repository depends on the label.

## 3. Reusing stage1 (`iso/stage_reuse.py`)

After every stage1 the builder writes `<storedir>/builds/23.0-default/livecd-stage1-amd64-<stamp>.tar.gz.receipt.json` (schema 1): archive name, size and SHA-512, Catalyst version, builder image id, `stage1_key`, the SHA-256 of each project source archive, and the name plus tree hash of each project ebuild directory.

* `stage1_key` hashes `iso/specs/livecd-stage1.spec`, everything in `iso/portage`, `iso/pins.env`, the wrapper, `make_conf_keys.py`, the `Containerfile`, the overlay's `acct-group`, `metadata` and `profiles`, and the constant `STAGE1_FORMAT` in `stage_reuse.py`. **Bump `STAGE1_FORMAT` when you change how `builder-entrypoint.sh` drives stage1.** Templates are hashed unrendered, so `JOBS` never invalidates a stage1. The stage2 spec, overlay, fsscript, menu and README do not belong to the key.
* **reuse**: key, Catalyst version and archive SHA-512 equal, and no project package changed: run stage2 only, from the archive (`options = ["pkgcache"]`, never `seedcache`, so a retained chroot cannot win over the verified archive).
* **reseed**: only project packages changed. `--reuse auto` does not use it: it builds stage1 fresh in this case, because the first real reseed reinstalled nothing and left the old installer in the image while the receipt described the new one. A reseed runs only for `BUILD_MODE=reseed` inside the container, and no real build has proved it since the fix. It copies the old archive to `...-completed.tar.gz` and runs a stage1 spec with that `source_subpath`. Catalyst copies `EMERGE_DEFAULT_OPTS` from its own environment into the chroot (the `envvars` of `catalyst.conf` only name variables; a value written there is ignored), so the builder exports it with `--reinstall-atoms=<each changed package>` added for this one run. Then the copy is removed and `stage_reuse.py reinstalled` reads `var/db/pkg/<atom>-*/BUILD_TIME` of every changed package from the new archive: one that was built before the reseed started was not reinstalled, and the build stops without writing a receipt. Only then is the receipt rewritten and stage2 run. Reseed never removes packages, which is why any change of the spec or the Portage configuration forces a fresh stage1.
* **fresh**: anything else, including a missing, symlinked or tampered archive, an unknown receipt schema or a different Catalyst.

To try a reseed for real, build once, edit a source file, and run the builder container with `BUILD_MODE=reseed` (the variables `build-iso.sh` passes, with that one changed); then check that the installed `.py` files in the ISO equal `src/` and compare `manifest.json` (`reused_stage1`, `stage1_mode`, `build_inputs_sha256`). Until that has been done, `--reuse auto` stays on a fresh stage1. Releases should be built with `--reuse none` unless the receipt shows `reuse`.

## 4. What `scripts/verify-iso.py` checks

Rules live in `iso/image-contract.json`; items with `when_source` apply only while that file exists in the repository, or while `pyproject.toml` declares the console script (`gentoo-rescue`, `gentoo-installer-text`, `gentoo-rescue-gui`, and the seven of the AI rescue package: `gentoo-rescue-agents`, `-login`, `-ai`, `-do`, `-approver`, `-mount`, `-share`). A required path can also name a `mode` (`/mnt/rescue` must be 0700). Exit status 0 passed, 1 a check failed, 2 the ISO could not be read.

| Area | Checks |
|---|---|
| ISO | Volume label equals the pinned one (`_TESTKEY` for a test image) and has at most 32 characters; exactly one BIOS and one UEFI El Torito image; hybrid MBR + GPT (USB sticks); required files: `boot/gentoo`, `boot/gentoo.igz`, `efi.img`, `efi/boot/bootx64.efi`, **`efi/boot/bootia32.efi`**, `efi/boot/grubx64.efi`, `efi/boot/mmx64.efi`, `README.txt`, `SECURE-BOOT.txt`, `ENROLL_THIS_KEY_IN_MOKMANAGER.cer`, `memtest64.bios`, `memtest.efi64`; GRUB module directories for `i386-pc`, `x86_64-efi`, `i386-efi`. |
| `grub.cfg` | At least 13 entries; `default=0`, positive `timeout`; every `linux` line is `/boot/gentoo` with the pinned boot arguments and `root=live:CDLABEL=<label> rd.live.dir=/ rd.live.squashimg=image.squashfs cdroot`, an `initrd /boot/gentoo.igz` and `search ... -l <label>`; the default entry starts the desktop with no `dokeymap`; `dokeymap` only together with `nox`; entries with `nox`, `nomodeset`, `rd.live.ram=1`, serial console, `acpi=off`, `rd.debug`; the entries "Repair a system (text console)", "AI rescue (text console)" and "Install in text mode" with `nox dokeymap gentoo.autostart=rescue` / `ai-rescue` / `installer-text`, and `gentoo.autostart=` only with a known value and only together with `nox`; no "safe graphics" title; unique titles (no Memtest block twice); Memtest entries exist when the images are in the ISO. A rendered `livecd-stage2.spec` must agree on label and boot arguments. |
| kernel configuration | `boot/gentoo-config` (wave 6, `kernel_config.required`): `SECURITY=y`, `SECURITY_YAMA=y` and `yama` in the comma list `CONFIG_LSM`. Yama built but not listed is not enabled, and then `kernel.yama.ptrace_scope` does not exist. See section 5a. |
| initramfs | `dmsquash-live` scripts and `dmsquash-live-root`; modules `isofs squashfs overlay loop usb-storage uas vmd sdhci-pci mmc_block dm-crypt raid1`; at least 20 console keymaps when an entry asks for `dokeymap`. |
| squashfs | Required files and types, commands (about 80: partitioning, file systems, LUKS/LVM/RAID, EFI, SMART, `cpuid2cpuflags`, `setxkbmap`, `links`, `thin_check`, and every live-side program of the repair tool such as `lsinitrd`, `jfs_fsck`, `script`, `chroot`, `timeout`, `modprobe`, `zstd` ...); every `livecd/rcadd` service as a runlevel symlink **and** an init script (plus Catalyst's own `autoconfig`, `xdm`, `fixinittab`, `syslog-ng`); `acpid` in no runlevel; the live GRUB's platform directories (`usr/lib/grub/i386-pc` and `x86_64-efi`, which `grub-install` needs when the repair tool has to install the boot loader from the live side); the polkit agent and its Xfce autostart file; `gentoo-chroot` and the console scripts of the repair tool and the text installer; forbidden paths (`/var/cache/binhost`, `/opt/rust-bin-*`, `/usr/share/doc`, static Qt libraries, `make.conf.old/.extra`, the Gentoo tree); **no entry owned by uid/gid 1000 or by the build user's HOST_UID/HOST_GID** outside `home/gentoo` and the live user's mailbox; root directory owned by root; content rules (`lvmlocal.conf`, `mdadm.conf`, `ACPI="no"`, logind drop-in, Hidden screensaver, no `rtcsync`, a browser in `helpers.rc`, a live `make.conf` without `MAKEOPTS`, `NINJAOPTS`, `EMERGE_DEFAULT_OPTS`, `DISTDIR`, `buildpkg` or `ACCEPT_LICENSE="*"`, greeting texts); required and forbidden packages (`dev-lang/rust-bin`, `sys-boot/shim`, `net-misc/netifrc`); the flavour rules above; **the account `rescue-ai`** (`squashfs.accounts`, wave 6): a system account (uid below 1000) with its own group as primary group, in no other group (`tty wheel disk video input audio plugdev usb kvm portage` are named in the message), locked in `/etc/shadow`, mentioned in no sudoers or doas file, and no sudo or doas rule for all users that would cover it anyway; the AI rescue files and console scripts, when the sources have them. |

Run on the accepted r19 image the squashfs rules fail exactly where this change set changes the image (43 overlay entries owned by 1000:1000, `acpid` enabled, no `chronyd`, rust-bin present, a builder `make.conf`, the new packages missing), and pass where nothing changed; that is the red test for I10. `tests/iso/test_verify_iso.py` also builds a small ISO with xorriso and gensquashfs from the repository's own overlay and runs the real contract against it, in both flavours, and again with parts taken away.

### When a check stops the build

* **The image check fails** (`the ISO failed the image checks; nothing was published`): the finished ISO stays in `<cache>/catalyst/builds/23.0-default/`. Run `scripts/verify-iso.py <that file>` for the full list of failed rules, fix the cause (or the rule in `iso/image-contract.json` if the rule was wrong) and run `scripts/build-iso.sh --stage2-only`: stage1 is reused, so this takes minutes, not hours.
* **The Gentoo commit is refused** (`verify-snapshot:` in the log, either while the builder image is made or at the start of a build): the commit of `GENTOO_TREEISH` is not signed, is signed by another key than `GENTOO_TREEISH_SIGNER_FPR`, or its signer is missing from the keyring of `sec-keys/openpgp-keys-gentoo-developers` in the bootstrap tree (a very new key). Check the commit by hand (`git verify-commit`), then pin the commit that you verified together with its signer in `iso/pins.env`. The check cannot be switched off from the command line on purpose.
* **`stage2-only` is refused** (`no receipt`, `sha512`, `specs, Portage configuration or pins changed`): stage1 is out of date; build once without `--stage2-only`.

## 5. Boot menu

`iso/cd_overlay/boot/grub/grub.cfg.in` is rendered to the overlay and **replaces** Catalyst's three-entry menu.

1. Gentoo installer and rescue desktop (default, no keymap prompt)
2. Desktop in RAM, label says "needs 6 GiB" (the squashfs is 2.8 GB; with the overlay and the desktop 6 GiB is the sane figure)
3. **Safe graphics (for a black screen or no picture)**: `nomodeset`, the desktop on the generic display driver (section 9). Third in the menu, so that somebody with a black screen finds it without opening the submenu.
4. **Repair a system (text console)**: `nox dokeymap gentoo.autostart=rescue`. The login on tty1 starts `sudo gentoo-rescue` once (see below).
5. **AI rescue (text console)**: `nox dokeymap gentoo.autostart=ai-rescue`. The login on tty1 starts `sudo gentoo-rescue-ai` once (section 5a). The only entry with an approver service.
6. **Install in text mode**: `nox dokeymap gentoo.autostart=installer-text`. The login on tty1 starts `sudo gentoo-installer-text` once.
7. Text console only: `nox dokeymap`, a plain shell (asks for a console keymap, which is needed for LUKS passphrases)
8. More options: verbose (`ignore_loglevel loglevel=7 rd.debug`), compatibility (`nomodeset pcie_aspm=off nvme_core.default_ps_max_latency_us=0 usbcore.autosuspend=-1`), serial console (`nox console=tty0 console=ttyS0,115200n8`), old firmware (`acpi=off noapic nomodeset`; both nomodeset entries use the generic display driver like Safe graphics), IOMMU off, text console in RAM (4 GiB)
9. Memtest86+ (BIOS and UEFI; Catalyst's own block, guarded by `[ -e ... ]` at boot time, present once)
10. UEFI firmware settings (`insmod efifwsetup; fwsetup`), continue with the next boot device (`exit`), restart, power off

Details that matter: `nox` is honoured by `gui-libs/display-manager-init` (its setup script touches `/run/.nogui`, `start_pre` refuses), and by livecd-tools' `autoconfig` (`X11=no`, `chvt 1`), so the project's `xdm` shim stays as it is. `secureconsole` stays in the boot arguments: livecd-tools' `fixinittab` then logs in only tty1 (as the live user) and puts real login prompts on tty2-6. With the serial entry the **last** `console=` becomes the login console: serial only, root auto-login (the VGA getty is removed), which is what a headless machine wants.

**The text entries and the autostart hook.** `nox` is the plain token; the display manager does not start, so the entries work on a GPU the live kernel cannot drive. `dokeymap` is on both because a LUKS passphrase or an account password is typed in the tool, and the initramfs prompt is the only place where the console layout is chosen before the login. `gentoo.autostart=rescue`, `gentoo.autostart=ai-rescue` and `gentoo.autostart=installer-text` mean nothing to the kernel (a parameter with a dot is ignored); `/etc/profile.d/20-gentoo-autostart.sh` reads them from `/proc/cmdline`. On the **first console login of an interactive text session** (tty1, no `DISPLAY`) it waits up to 20 s for the installer service socket, runs `sudo gentoo-rescue`, `sudo gentoo-rescue-ai` or `sudo gentoo-installer-text` in the foreground (for `ai-rescue` it waits up to 20 s more for `/run/gentoo-rescue/do.sock`, the approver's socket; the plain repair token wins when both are given), and prints how to start it again when it ends or fails. A `mkdir` of `/tmp/.gentoo-autostart` is the one-time switch, so the autologin that follows `exit` does not start it a second time. If `sudo` or the tool is missing it says so and the login continues. Another console, a script, scp or the desktop never start it. `etc/profile.d/10-gentoo-rescue-hint.sh` prints the commands on every text console (the AI line only when `gentoo-rescue-ai` is installed). The tokens and titles are checked by `scripts/verify-iso.py` and by `tests/iso/test_text_modes.py`, which drives the hook in a shell with stand-ins for `sudo`, `tty` and the tools.

**Safe graphics (H1).** The live kernel is `sys-kernel/gentoo-kernel` built from source by Catalyst (stage2, `USE=-initramfs`, then dracut), not the binary package: the binary has `# CONFIG_DRM_SIMPLEDRM is not set`, `# CONFIG_DRM_EFIDRM is not set`, `# CONFIG_DRM_VESADRM is not set`, `# CONFIG_SYSFB_SIMPLEFB is not set`, so under `nomodeset` there is no DRM node and Xorg cannot start. The package `app-admin/gentoo-live-installer[safe-graphics]` installs `files/live-safe-graphics.config` as `/etc/kernel/config.d/50-gentoo-live-safe-graphics.config` in stage1; the kernel-build eclass merges it when stage2 builds the kernel (`DRM=y`, `SYSFB_SIMPLEFB=y`, `DRM_SIMPLEDRM=y`, `DRM_FBDEV_EMULATION=y`, and `DRM_EFIDRM`/`DRM_VESADRM` which kernels from 6.16 have; their Kconfig excludes `SYSFB_SIMPLEFB`, so one family or the other ends up in the kernel). With the native GPU drivers kept away by `nomodeset`, the firmware framebuffer is a DRM device and Xorg's modesetting driver runs on it: no 3D, but a desktop on every PC. Rules that came out of reading Catalyst 4.2: the spec must not set `boot/kernel/gentoo/config` (for a distribution kernel Catalyst copies that file into `/etc/kernel/config.d` with `os.makedirs` and no `exist_ok`, which fails because the package already installed the directory); the `kerncache` option stays off (its cache test compares `/var/tmp/gentoo.config`, which only a genkernel build writes, so for a distribution kernel it never hits); `iso/portage/make.conf` adds `--usepkg-exclude=sys-kernel/gentoo-kernel` because a binary package from the binhost or from the local cache was built without the fragment. The kernel therefore builds on every stage2 run (about 30-60 minutes on top of the former 2-3 minutes of unpacking the binary kernel; an estimate, not measured). `verify-iso.py` reads `boot/gentoo-config` (Catalyst renames the kernel's `config-*` to `<kernel>-config`) and requires one complete family (`SYSFB_SIMPLEFB=y` with `DRM_SIMPLEDRM=y|m`, or `DRM_EFIDRM` with `DRM_VESADRM`); a driver built as a module must be in the initramfs. It also requires the "Safe graphics" entry with `nomodeset` and without `nox`. Not tested in a VM here: the harness boots the entry (H04).

### 5a. The AI rescue stick (wave 6)

The entry "AI rescue (text console)" runs `gentoo-rescue-ai` (package `src/gentoo_rescue_ai`, written by the ai owner) as root on tty1: it offers Wi-Fi and `gentoo-rescue-mount` (the disk passphrase is typed here, as root), shows the per-boot password, and opens a tmux session in which the agents (Claude Code, Codex, OpenCode, installed on first use) run as the user `rescue-ai`. The disc's part, and the reasons for it:

* **The account.** `iso/fsscript-stage2.sh` runs `useradd -r -m -k /etc/skel-rescue-ai -U rescue-ai`: a system account (uid below 1000, so apart from the live user 1000 and from the ownership rule), its own primary group, **no `-G`**, `passwd -l`, home 0700 (the contract requires that mode). The skeleton is `/etc/skel-rescue-ai` from the package's data tree (Codex's `config.toml`, OpenCode's `opencode.json`, the `AGENTS.md` symlinks); the build continues without `-k` when the tree is absent. The script then stops the build when `id -nG rescue-ai` is anything but `rescue-ai`, when the uid is 1000 or more, or when a sudoers/doas file names it or has a rule for ALL users. `scripts/verify-iso.py` repeats this on the finished image from `/etc/passwd`, `/etc/group`, `/etc/shadow`, `/etc/sudoers` and `/etc/sudoers.d/*` (`accounts.exists`, `accounts.weak`).
* **Why not `wheel` and why a polkit rule.** Catalyst's `livecdfs-update.sh` creates the live user with `-G users,wheel,audio,plugdev,games,cdrom,disk,floppy,usb` and removes the comment from the `NOPASSWD: ALL` line of `/etc/sudoers` (the wheel rule); `pam_wheel` also guards `su`. The live user has an **empty password**, and polkit's administrators are the group wheel, so an agent running `pkexec` would be authenticated by the live user's empty password. `iso/root_overlay/etc/polkit-1/rules.d/00-gentoo-rescue-ai.rules` answers NO to everything for `rescue-ai` (rules are read in name order and the first answer wins). `su` is already refused by `pam_wheel`, `sudo` has no rule, and `sshd` refuses empty passwords (section 6). Other ways from `rescue-ai` to the live user were looked for and not found: `/home/gentoo` is 0700, the tty devices belong to the live user and `rescue-ai` is in no `tty` group.
* **The approver service.** `app-admin/gentoo-live-installer[rescue-ai]` installs `/etc/init.d/gentoo-rescue-approver` and `/etc/conf.d/gentoo-rescue-approver` (`RESCUE_VT=9`, `RESCUE_APPROVER_ALWAYS="no"`); `livecd/rcadd` puts it in the default runlevel of every boot, but its `start()` does nothing unless `/proc/cmdline` has the whole word `gentoo.autostart=ai-rescue` (so no other entry has a socket, a password or an approver; OpenRC has no per-entry runlevel without more machinery). Nothing but OpenRC starts it (a test greps the sources). `start_pre` takes the first free console from tty9 (`fuser -s`), makes `/run/gentoo-rescue` (root:rescue-ai 0710: the agents may enter, not list) and `/var/log/gentoo-rescue` (root 0700, the audit log), removes anything left from an earlier start, makes the password and runs `gentoo-rescue-approver --vt N --socket /run/gentoo-rescue/do.sock --audit /var/log/gentoo-rescue/do.log`. The approver must stay in the foreground (OpenRC backgrounds it with a pidfile). The password: twelve characters from an alphabet without look-alikes (`abcd-efgh-jkmn`, about 59 bits), from `/dev/urandom`, written under `umask 077` to `/run/gentoo-rescue/do-password` (root:root 0600); the service never prints it. The approver shows it on its VT and `gentoo-rescue-ai` shows it on tty1, as root, before it opens the tmux session. The socket file's mode (0660 root:rescue-ai) is set by the approver. `tests/iso/test_approver_service.py` runs the init script under `sh` with stand-ins for OpenRC.
* **Yama.** `kernel.yama.ptrace_scope = 1` in `iso/root_overlay/etc/sysctl.d/60-gentoo-rescue-ai.conf`, applied by OpenRC's `sysctl` service (boot runlevel, in `implicit_services` of the contract). The live kernel needs Yama built in **and named in `CONFIG_LSM`**. The base configuration of `sys-kernel/gentoo-kernel` is a distfile that was not readable while this was written, so `files/live-rescue-ai.config` (installed as `/etc/kernel/config.d/51-gentoo-live-rescue-ai.config` by `[rescue-ai]`, merged by the kernel-build eclass like the Safe graphics fragment) sets `CONFIG_SECURITY=y`, `CONFIG_SECURITY_YAMA=y` and `CONFIG_LSM="landlock,lockdown,yama,integrity,bpf"`, and `verify-iso.py` fails the build when the final `boot/gentoo-config` lacks any of that (`kernel.yama`): the gate is the finished image, not the fragment. No boot entry passes `lsm=` (a test checks), which would replace the list.
* **Packages.** `media-gfx/qrencode`, `www-apps/ttyd`, `sys-apps/ripgrep` and the SystemRescue-style tools (`snapper fsarchiver ncdu tcpdump mtr dd-rescue dislocker foremost memtester restic rclone cifs-utils vim mc`) are in `livecd/packages` and in the contract's `required_packages`, their programs in `squashfs.commands` and `required_commands` of the fsscript; each atom was read in the tree and `iso/check-atoms.py` passes. **ttyd** is kept at the exact `=www-apps/ttyd-1.7.7-r2 ~amd64` (`package.accept_keywords`). `-r1` is `KEYWORDS="amd64"` in the pinned tree and would need no keyword, but it accepts any `libwebsockets >= 4.4`, which resolves to the stable 5.0.0, while `-r2` differs from it only by pinning `=libwebsockets-4.5*`: a revbump that does nothing else is the usual sign that the newer series broke the build, and `check-atoms.py` does not follow dependencies. The tree could not be asked for the reason (no git history in `/var/db/repos/gentoo`); drop the keyword when a later ttyd is stable. It needs `net-libs/libwebsockets[libuv,ssl]`, set in `package.use`. `net-fs/cifs-utils` is built with `-ads -python` (no Kerberos, no Python helpers: `mount.cifs` is what a rescue needs). `rclone` needs `sys-fs/fuse:3` next to the pinned `fuse:0` (they are separate slots). The runtime programs of the AI tool (`tmux openssl qrencode kbd ripgrep ttyd`) are `rescue-ai?` dependencies of the installer package, with a blocker on `dev-util/claude-code`, which installs the same `/etc/claude-code/managed-settings.json` as the data tree of this package; the agents themselves are never in the image (first-use download, the ai owner's `gentoo-rescue-agents`).
* **The package's files.** With the flag on and `src/gentoo_rescue_ai/data/root` in the sources, `src_install` copies that tree to `/` with `cp -a` (modes and symlinks kept, nothing edited) and removes group/other write from `/etc/gentoo-rescue` and `/etc/claude-code`. The contract requires `/etc/gentoo-rescue/AGENTS.md`, `/etc/claude-code/CLAUDE.md`, `/etc/claude-code/managed-settings.json`, `/etc/skel-rescue-ai` and the seven console scripts, each only while the sources have them.
* **Writing the stick.** `iso/README-live.txt` explains `dd`, `caligula`, Rufus in DD Image mode and balenaEtcher (the ISO is a hybrid image; ISO mode and file-copying tools do not give a bootable stick; there is no persistence), and section 10 of it describes the AI entry, the approval console and the risks in plain words.
* **Not done.** The H1 leftover "kerncache" is not touched: the kernel cache of Catalyst compares a file that only a genkernel build writes, so for the distribution kernel it never hits (section 5, Safe graphics); a cache would have to be a binary package built with the fragments, which is a change of the build design and not small. A VM test of the whole chain (the entry boots, the service runs, an agent cannot open `/dev/tty1` or the approver's VT, `chvt` and `TIOCSTI` fail, `ptrace` is refused) is the harness owner's; nothing here was booted.

### Remote access (I9, the image half)

`sshd|default` is in `livecd/rcadd` of the release spec, so every flavour starts sshd at boot; the test flavour no longer adds it (`configure_test_access` writes only the key, the marker, the banner and the test drop-in). Nobody can log in until a password is set on purpose: root is locked, the live user `gentoo` has an empty password, and `etc/ssh/sshd_config.d/10-gentoo-live.conf` says `PermitEmptyPasswords no` (the default, written down so that a later default cannot open that account). sshd takes the first value of most keywords and reads the drop-ins in name order, so this file (`10-`) comes before Gentoo's `9999999gentoo-livecd.conf` (`PermitRootLogin Yes`, as on the official media: `sudo passwd root`, then `ssh root@ADDRESS`, the Handbook's way). The test drop-in `90-installer-vm-test.conf` sorts before `9999999...` too, which is how a test image gets key-only root login (`PermitRootLogin prohibit-password`, first in name order). `sudo gentoo-remote-access on|off|status` (a bash script installed by the live package) sets or removes the live user's password (a readable one such as `fox-oak-sun42` is made when none is given), starts sshd if needed and prints `ssh gentoo@ADDRESS`, the password and the host key fingerprints; `/etc/motd` and `/etc/issue` name it and the Handbook's way. The image carries no host keys: `livecd/rm` removes `/etc/ssh/ssh_host_*`, the contract forbids them, and the sshd init script makes new ones at each boot. `verify-iso.py` also checks, in name order, the first `PermitEmptyPasswords` (`no`, both flavours) and `PermitRootLogin` (`prohibit-password`, test flavour). The daemon actions `remote_status|remote_enable|remote_disable` are the backend's (`src/gentoo_installerd/remote.py`).

## 8. Packaging

`packaging/gentoo-overlay`: vendored packages (section 11), and `gentoo-live-installer-0.1.0-r5` (flag `rescue-ai` since wave 6; one revision only: `build-iso.sh` and the builder insist on exactly one ebuild per package; a changed ebuild needs no new revision, because a build always builds the project's packages again from this tree), `hwmonux-1.0.0-r1`, `portagehub-0.4.0-r1` (its sources are the PortageHub repository, imported by `scripts/sync-app.sh portagehub` into `apps/portagehub`; `apps/portagehub/UPSTREAM` names the commit, and the live CD's own change to it is the patch in `files/`), `app-admin/gentoo-settings-0.1.0` and `sys-kernel/kernelsmith-0.1.0` (the user's Gentoo Settings and KernelSmith, imported the same way by `scripts/sync-app.sh gentoo-settings` and `scripts/sync-app.sh kernelsmith`; KernelSmith from a `git clone --mirror` of its GitHub repository in `.cache/upstream/kernelsmith.git`; the builder vendors the crates of all three Rust applications, `RUST_APPS` in `iso/builder-entrypoint.sh`), `acct-group/gentoo-installer`, each with a `metadata.xml`. The distfiles are produced by the builder, so the ebuilds have `RESTRICT="mirror fetch"` and a `pkg_nofetch` message; Manifests are generated at build time (thin manifests), which is the one pkgcheck finding that stays (`ISO_RUN_PKGCHECK=1` runs pkgcheck on a copy and allows exactly that, `PythonCompatUpdate` for python3_15 which the stable pyside lacks, and the unstable `liquidctl` behind its flag).

* RDEPEND of the installer lists every program the daemon, the hardware probe and the repair tool run. `tests/iso/test_ebuilds.py` maps every entry of `REQUIRED_TOOLS`/`OPTIONAL_TOOLS` in `inspect.py`, of `TOOLS_WANTED` (`rescue/hostenv.py`), of `CHECK_TOOLS` (`rescue/fsprobe.py`) and every program that the host policy of the repair tool (`rescue/safety.py`) has a checker for to an atom (`TOOL_PACKAGE`), and fails when one is not mapped, when its package is not in RDEPEND, or when the stage2 fsscript or the image contract does not check for it. A new program therefore needs four edits in one change: the package in RDEPEND, `TOOL_PACKAGE`, `required_commands` in `iso/fsscript-stage2.sh` and `squashfs.commands` in `iso/image-contract.json`. The file system checks of the repair tool (F2FS, exFAT, JFS, NTFS), GRUB (the live `grub-install` is the fallback when the repaired system cannot run its own), Dracut (`lsinitrd`), kmod, coreutils and zstd are unconditional. Btrfs, XFS, EFI and Secure Boot tools (`sbsigntools`, `mokutil`) sit behind `btrfs`, `xfs`, `efi`, `secureboot` (the live image has all of them).
* The ebuild is made for the live disc. The overlay is also copied to installed systems (`/var/db/repos/gentoo-live-installer`, so that HWMonux and PortageHub can be installed there). Emerging the installer package on such a system would pull GRUB, dracut and the file system tools of the repair tool.
* The rescue launcher `data/gentoo-rescue.desktop` (`Exec=gentoo-installer --mode repair`) and the helper `gentoo-chroot` (`exec gentoo-rescue chroot "$@"`, installed from `files/` with `dobin`) are installed when the sources contain `src/gentoo_installerd/rescue`. The console scripts `gentoo-rescue` and `gentoo-installer-text` (and `gentoo-rescue-gui`, if it ever exists) come from `pyproject.toml` (distutils-r1 installs whatever it declares); the image contract requires each of them only when `pyproject.toml` declares it. The motd, the boot menu and the disc's README name both, so `pyproject.toml` must declare them when the tools ship: `tests/iso/test_text_modes.py` fails once `src/gentoo_installer/textui` exists without `gentoo-installer-text = "gentoo_installer.textui.cli:main"`, and `test_overlay_files.py` does the same for `gentoo-rescue`.
* HWMonux: `liquidctl` and `hidapi` are `~amd64` only, so the dependency sits behind a flag that is off by default: the ebuild solves on a stable system, and the live image enables it. `drivetemp` is loaded from `/etc/modules-load.d/hwmonux.conf`; Super I/O drivers (`nct6775`, `it87`) are never loaded automatically because probing can hang an embedded controller; `sensors-detect` stays a manual step.
* Services: OpenRC runs the daemon as root without D-Bus, logs to `/var/log/gentoo-installerd.log` and allows 60 s for the SIGTERM clean-up; systemd uses `KillMode=mixed`, `TimeoutStopSec=60`, `RuntimeDirectory=gentoo-installer`. A supervisor (`supervise-daemon`) was not enabled because it cannot be tried without an OpenRC boot; `Restart=on-failure` stays for systemd only.

## 9. Known limits and follow-ups

* **Safe graphics (review H1)**: done (section 5): the kernel is built from source with the fragment, the entry exists and `verify-iso.py` checks the symbols. What is not known until a build: that the fragment really leaves `DRM_SIMPLEDRM` built in (`verify-iso.py` fails the build otherwise, after the long part), the build time of the kernel, and that Xorg's modesetting driver starts on `simpledrm` on real GPUs (the VM test of the entry is the harness's H04; NVIDIA with the proprietary driver is a different case: the installed system needs the Safe graphics entry of its own boot loader, not this one).
* **Speech output (review IMG-2)**: the disc has no screen reader, speech or braille software. Catalyst's stock "accessibility" entry passed `dospeakup`, which livecd-tools 2.11 does not read (`init.d/autoconfig` knows `speakup.synth=NAME`: it loads `speakup_NAME`, switches the desktop off and starts `espeakup` for `soft`), and nothing on the image could speak, so the entry booted the normal desktop in silence; it was removed, with its contract item and test. The kernel has the modules (`speakup_soft.ko`). A sketch of what a real entry needs, untested here: `nox speakup.synth=soft` in the entry; `app-accessibility/espeakup` (0.90-r3, stable) and its `espeak-ng[sound]` in `livecd/packages`; `media-sound/sox -ffmpeg` in `iso/portage/package.use` (espeak-ng needs sox, whose `ffmpeg` flag is on by default); `media-libs/pcaudiolib -pulseaudio` so that speech goes through ALSA, which `autoconfig` unmutes, and not through a sound server that does not run under `nox`; `/etc/modules-load.d/espeakup.conf` under `livecd/rm` in the stage2 spec (it would load `speakup_soft` on every boot); a contract that requires the argument, `etc/init.d/espeakup` and the package; and a VM scenario with a sound device that checks `espeakup` runs and `/sys/accessibility/speakup/synth` says `soft`. The spec change makes the next build a fresh stage1.
* **Secure Boot (live disc only)**: `iso/sign-secure-boot.py` runs after Catalyst (`publish_iso`) and before `verify-iso.py`. It makes an RSA-2048 key for this ISO in `/dev/shm`, builds a standalone GRUB with every module the menu needs (`GRUB_MODULES`, Gentoo's `sbat.csv`, `grub,5`), signs it and `/boot/gentoo`, and destroys the key. It writes a new `/efi.img` (label `GENTOO_EFI`): Fedora's shim from `sys-boot/shim` as `BOOTX64.EFI` (signed by Microsoft's UEFI CA 2011 and 2023), MokManager, the signed GRUB, Catalyst's unchanged `BOOTIA32.EFI` and the certificate. The same files go to `/efi/boot` in the ISO 9660 tree. The hybrid boot setup is written again with grub-mkrescue's options, because `-boot_image any replay` fails on these images ("GPT partitions 1 and 2 overlap"). That setup has no HFS+ part: Intel Macs start the EFI partition. The certificate is published as `<iso>.secureboot.cer`, with its MokManager fingerprint in `<iso>.secureboot.txt`. The installed system's GRUB stays unsigned (BOOT-08). `verify-iso.py` checks the files, shim's Microsoft signature, that GRUB, the kernel and the tree copy verify against the disc's certificate, and the SBAT generation (contract `secure_boot`). With Secure Boot on, QEMU's standard VGA shows the GRUB menu garbled in screendumps; virtio-vga does not, and the menu still works.
* **32-bit UEFI (review H6)**: `bootia32.efi` and `i386-efi` are on the ISO because the builder image sets `grub_platforms_efi-32` and `grub-mkrescue` runs in the builder; `iso/portage/make.conf` `GRUB_PLATFORMS` only concerns the GRUB inside the live root. The kernel has `CONFIG_EFI_MIXED=y`. A boot test with edk2-i386 in QEMU is still to be run by the harness.
* **Kernel age (review H11)**: Linux 7.2.13, the newest `gentoo-kernel` of the pinned tree (`iso/portage/package.accept_keywords/live-installer` accepts `~amd64`), and that tree's firmware. Hardware released later may lack drivers; a newer kernel needs a new pin.
* **Network shares**: `net-fs/cifs-utils` is on the disc since wave 6 (built with `-ads -python`, so no Kerberos and no Python helpers; `mount.cifs` only), `nfs-utils` is not. A package added to a build that cannot be tested here is paid for with hours of rebuild if it fails. OpenSSH and rsync are on the disc, so data leaves a broken machine over `rsync -a` or `scp` to another computer, or to a USB disk. Adding cifs-utils later is one atom in `livecd-stage1.spec`; the changed spec makes the next build a fresh stage1.
* **Not in this change set**: the live hardware service (`gentoo.xkb=`/`gentoo.tz=` boot parameters, HiDPI helper, touchpad defaults), the daemon holding a logind inhibitor during an install (`elogind-inhibit`, the lid is already ignored by the drop-in), `accept-iso.py` (binds VM results to the ISO hash), the sha256 of the binhost `Packages` file in the manifest, and a real run of the reseed (`BUILD_MODE=reseed`, see section 3). Each is listed in the integration notes of the change.
* **Manual checks on a build** (QEMU, then real hardware): boot each menu entry under SeaBIOS and OVMF (and edk2-i386); the text console entries show no `display-manager` process and a tty1 login; "Repair a system (text console)" starts `gentoo-rescue` and "Install in text mode" starts `gentoo-installer-text` after the keymap prompt and only once; "AI rescue (text console)" starts `gentoo-rescue-ai` (waiting for `/run/gentoo-rescue/do.sock`), `rc-status` shows `gentoo-rescue-approver` and `ps` an approver on tty9 (stopping the service on any other entry must not complain about a missing pid file) (and no approver in any other entry), `/run/gentoo-rescue/do-password` is 0600 root, `cat /proc/sys/kernel/yama/ptrace_scope` is 1, `id rescue-ai` shows one group, and from the agent pane `cat /dev/tty1`, `cat /dev/tty9`, `chvt 9` and `pkexec true` all fail; `sudo gentoo-rescue` finds an installed Gentoo disk and lists a Debian one as "Not a Gentoo system" without opening it; a polkit dialog appears for GParted on the desktop and takes an empty password; the serial entry logs in on `ttyS0`; Memtest86+ starts; "UEFI firmware settings" opens the setup; `rc-status` shows `chronyd` and no `acpid`; with a laptop, close the lid on battery and on power during an install and confirm it stays awake; plug in a disk with an LVM volume group and a RAID array and confirm they stay inactive until the repair tool activates them.

## 11. The companion overlay and the pin-bump checklist

**Vendored ebuilds (hardware I01).** `packaging/gentoo-overlay` is the repository the live disc builds from and the installed system gets as `/var/db/repos/gentoo-live-installer` (copied to `/usr/local/share/gentoo-installer/overlay` on the disc, with the distfiles next to it in `.../distfiles`). Besides the project\'s own packages it carries pinned copies of ebuilds that the plan needs and that ::gentoo does not have. Today: `gnome-extra/iio-sensor-proxy-3.9` (auto-rotate and ambient light sensors for KDE and GNOME), copied from ::guru (`gentoo-mirror/guru` master at the commit the ebuild header names). Not vendored: `sys-power/rog-daemon` (item B13 is "could", and the user\'s decision sends the ASUS tools through the `edorp` overlay), and nothing that is in ::gentoo.

The policy:

* **Pinned by commit and by hash.** The header comment of the ebuild names the ::guru commit; the `Manifest` next to it is committed (the project\'s own packages have none; theirs is made at build time) and carries BLAKE2B, SHA512 and SHA256 of the tarball. Only the keywords differ from ::guru (`amd64` instead of `~amd64`, because everything it needs is stable; the copy then needs no `accept_keywords`); `tests/iso/test_vendored_ebuilds.py` compares the rest with a local ::guru checkout when there is one.
* **Distfiles on the disc.** The builder runs `ebuild ... fetch` (not `manifest`) for a package that has a committed Manifest, so a tarball that differs from the pin stops the build; the verified file is copied to `usr/local/share/gentoo-installer/distfiles`, so an install without a network builds it from the overlay.
* **Never ::guru itself.** Nothing runs `eselect repository enable guru`, `emerge --sync` for it, or adds it to `repos.conf` (a test greps for it). The overlay is added to an installation only when a plan atom selects a package from it, and the page that shows the plan says that the package is unofficial and compiled on this PC (the ebuild\'s `pkg_postinst` says so too). `iio-sensor-proxy` is for KDE or GNOME with a probed sensor only; the plan code (`src/gentoo_installerd/configure.py`, `hwplan.py`) decides, not this directory.
* **Not in the live image.** The live disc does not install it; it only ships the files.

**Pin-bump checklist (hardware I02).** Whenever `GENTOO_TREEISH` (and `GENTOO_TREEISH_SIGNER_FPR`, `STAGE3_*`, `SOURCE_DATE_EPOCH`) in `iso/pins.env` changes:

1. Update the pins as one reviewed change; `iso/verify-snapshot.sh` insists on the signer. Check the candidate with the keyring the builder will use, the tree's own `sec-keys/openpgp-keys-gentoo-developers` (for example from the image's emerge step: `/usr/share/openpgp-keys/gentoo-developers.asc`), not with Gentoo's live `active-devs` list: a developer's new signing subkey is in the live list weeks before the package has it, and the image build then stops with `ERRSIG ... 9` (no public key). Pick the newest commit that this keyring verifies.
2. Run `iso/check-atoms.py --tree <the new tree> --guru <a ::guru checkout>` (under `scripts/sandbox.sh`). It fails when an atom of `livecd/packages`, of the project\'s ebuilds, of `package.use` or of `--extra FILE` (the harness passes the atoms of the hardware plan) dropped to `~amd64`, disappeared, or when a pinned `=cat/pkg-ver` is gone; it fails when a vendored package is in ::gentoo now (delete the copy and its Manifest), and warns when ::guru has a newer version of one (copy it as a new pin: ebuild, `files/`, Manifest with all three hashes, commit named in the header). `ISO_TREE=<tree> tests/iso` runs the same check as a test, plus the USE-flag, licence and package-existence tests.
3. Re-run the harness\'s checks that depend on the tree and are not this directory\'s: tree evidence for the hardware plan\'s atoms and the desktop resolve matrix (`scripts/lint-plan.py`, `scripts/resolve-gate.py`), and refresh the NVIDIA PCI-id slice the plan embeds.
4. Re-read the facts the image relies on: that `xfdesktop` still names `/usr/share/backgrounds/xfce/xfce-x.svg` (the fsscript checks it), that Gentoo\'s `sshd_config` still has the `Include` line first and `openssh[livecd]` the same drop-ins (section 6), and that the kernel Kconfig still lets `SYSFB_SIMPLEFB` and `DRM_SIMPLEDRM` coexist (`verify-iso.py` checks the result).
5. Build with `--reuse none`; the changed spec or pins make stage1 fresh anyway.

`iso/check-atoms.py` does not follow dependencies of dependencies; that is `scripts/resolve-gate.py`\'s job.
